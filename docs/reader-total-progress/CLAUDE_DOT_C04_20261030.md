## What the workflow does (one job, ubuntu-22.04)

1. `scope` – HEAD equals `GITHUB_SHA`, base is an ancestor, every changed path is an owned path.
2. `selftest` – plants a run-time canary in raw / hex / base64 (3 alignments, std+url) / percent /
   UTF-16LE form and in a file name and requires the scanner to find each; a clean tree must pass;
   too-short canaries are refused; the static detectors must flag unpaired `mkstemp`, unmanaged
   `TemporaryDirectory` and secret-named log arguments and accept the paired/`with` forms.
3. `static` – tracked production code (`src include extras apps examples tools bindings`, minus tests
   and vendored dirs): every temp-file/dir creation site is classified (cleanup-paired within ±150
   lines, auto-unlinked `tmpfile`, context-managed, or **unproven**); log/print lines passing
   credential-named values; informational user-path inventory. No username/file/identifier allowlist.
4. `build` – the unchanged `extras/credentials` module is built and installed; a new probe
   (`consumer/probe.c`) links the installed package only.
5. `dynamic` (`run_dynamic.py`) – private `dbus-daemon` + `gnome-keyring-daemon`, temporary
   HOME/XDG/TMPDIR, canaries generated at run time (never real credentials). Phases: argument
   validation leaves store untouched; absent → put → verify → replace → verify → delete → absent;
   locked collection and missing service must refuse (UNAVAILABLE/IO) with no plaintext fallback.
   After every phase the whole sandbox (contents and file names) and the probe's stdout/stderr are
   scanned for both canaries in all encodings, and TMPDIR must be empty. Sandbox removal is checked.
6. `summary` – binds repository, SHA, run id, attempt, job, OS/arch/image, probe and library SHA-256,
   report hashes; all four gates must pass. Uploads `build/f10/reports/` (no logs, no secrets).

## Static findings (honest, not suppressed)

* **Genuine deficiency (Apple, production):** `examples/apple/HostWave3Views.swift:372`
  `reviewDirectory()` creates `<temporaryDirectory>/wave3-review-<UUID>` for annotation
  export/review actions; no `removeItem` for it exists anywhere in the repository
  (`grep wave3-review` hits only this function and a diagnostic workflow). Exported annotation
  data therefore stays in the app temp directory until the OS purges it. Fixing needs a parent
  approved Apple production edit — NOT done here (Apple paths belong to other owners).
* The other 8 initial "unproven" hits were Python `with tempfile.TemporaryDirectory()` forms and an
  import line, i.e. detector false positives; the detector was corrected (and self-tested both ways)
  rather than any file being allowlisted.
* No credential-named value passed to a log/print call was found (line-based; multi-line calls and
  wrappers are not seen).
* User-path inventory (informational): 3 tool scripts contain a `/home/<name>`-style literal.
