# 原生轻量阅读核心工作包

2026-10-22。当前执行路线；取代历史二十项队列作为下一核心版本的排期依据。
定位：保留多格式解析、自有 PDF 渲染和 C SDK，不依赖 WebView，优先正确性、轻量、低延迟与有界内存。
本文件登记待执行任务；不代表对应代码或云端验收已完成。

## 六个工作包

| 包 | 目标与交付 | 验收出口 | 依赖与并行边界 |
| --- | --- | --- | --- |
| R1：标准阅读构建 | 新增可复现的 `reading-core` 构建配置：保留现有重排格式和 PDF/CBZ；音频、书库、全文索引、PDF 编辑及工具按需选择；另登记带书库的宿主组合 | 云端安装后公开 C/C++ 消费；依赖和符号核对；原生无 WebView；报告库、必要依赖、字体/资源分列大小；新增配置不破坏原构建契约 | 可立即独立做；拥有构建 preset/组件安装配置，需与 R6 协调工作流 |
| R2：实际阅读故障 | 从已有清单冻结代表性 EPUB/PDF 集合，包含常用文件、历史超时/打开/绘制故障；登记来源、许可、散列、预期和限界 | 每份实际打开、渲染与文字/位置核对；修复需有失败回归；参考引擎仅用于疑点差分；失败/拒绝/超时分列，不事后修改预期 | 清单与诊断可立即做；引擎改动与 R4 按文件协调；保留 0/1710 等历史记录，不能用小集合改称全量通过 |
| R3：体积与性能基线 | 复用 benchmark，补齐 PDF 和固定随机跳页等缺项；固定源码、构建、字体、页面、质量、设备/runner、线程、缓存条件与采样方案 | 打开/首屏、翻页/跳页 p50/p95、峰值 RSS、解析/缓存载荷和体积均有原始样本；失败也计入；冻结绝对预算和回归容差 | 工具准备可并行；正式基线等 R1 配置及 R2 初始清单冻结；拥有测量工具，不同时改引擎热点 |
| R4：核心性能收口 | 依据 R3 的热点逐项优化解析、布局、PDF 绘制、缓存与分配；每项保留前后同条件数据 | 正文/位置/代表页质量不退化；速度、内存、体积联合报告；预算满足，未解释的回归阻断；无热点证据时不重写 | 等 R3 有可复现热点再启动；与 R2 修复串行合入共享引擎文件 |
| R5：宿主有界接入 | 每个平台独立子任务，重排阅读接入 publication pager；书库来源、进度/标注、随机恢复、取消、关闭与旧任务隔离一并验证 | 云端真实宿主路径完成打开/翻页/跳页/重启；长章用有界入口并计量；原生 UI；不在 UI 线程做长解析；各平台单独授予通过 | 不阻塞无 UI 核心 SDK 发布；先选一个宿主闭环，再复用；Android A 先完成其现有失败收口 |
| R6：核心发布门槛 | 把阅读核心、宿主和可选扩展明确分组；建立默认分支必需检查、核心预算门禁与发布流程；统一版本/tag/源码/工件/许可身份和 About 描述 | 必需检查及权限配置可核查；失败/跳过/缺证据不能发布；裁剪配置和标准核心安装消费通过；可选扩展有独立验收；新协议正反例通过 | 协议设计可立即做；正式启用等 R1/R2/R3 定义稳定，发布等待 R2/R4 的选定缺陷与预算收口 |

R1 的轻量配置通过组件选择实现。PDF 密码认证、必要图像/字体和显示正确性按声明场景保留，
新增裁剪必须明确支持边界，不能为了缩小体积静默退化已有标准配置。
R3 首轮用于确定预算，尚未测量的 MB/ms 数值留空；共享云 runner 的噪声和冷缓存不可控情况须登记，
不能把不同硬件的结果当作同一性能保证。
R2/R4 的解析和资源管理修复必须保留针对性畸形输入、取消、预算及 ASan/UBSan 回归；
R6 的核心门禁保留所有已声明格式的现有正确性回归。缩减功能排期不缩减已交付接口的质量要求。

## 并行与合入顺序

先并行准备 R1、R2 的清单/诊断、R3 测量工具和 R6 协议；共享构建文件由 R1 负责，门禁由 R6 负责。
冻结配置与初始语料后测基线，再按真实热点启动 R4。R2/R4 共享核心文件的改动逐项合入并验证。
R5 按平台独立分支推进，宿主采用哪个 SDK 必须登记固定源码；所有代码合入后按变化范围复验。
以一个平台建立首轮性能预算，其余平台完成正确性/构建验证并分别计量，避免一次启动全部平台优化。

所有构建、测试、语料生成、benchmark、模拟器和证据汇总在 GitHub Actions 执行；本地只做源码/文档和 Git 操作。
本轮路线更新不启动代理、测试或新的功能实现。

## 现有 A/B/C 如何收口

- A 保持当前 Android 回归修复及严格交付要求，先修失败，不追加新功能；有界入口接入放到 R5。
- B 保持至少 30 份独立 PDF 及保存/重开/外观的原验收，归入可选 `pdf_edit` 交付；完整表单能力不再作为未来只读核心发布前提。
- C 的阶段一/二已完成，K 为 `4729f7fc7d908d249704d96ee61cc74ee778a27f`。
  当前整合交付的阶段三/四仍按 A/B → H → OPDS → S → 12 组/33 上游作业与严格汇总的原契约执行。
  该组合验收与未来 reading-core 发布分开登记。

在此之前，现有严格汇总不会因本次文档调整减少 run ID、删除检查或把旧失败改为成功。
各外部工作树由原负责人维护；本次不修改其源码、分支或运行。

## 按需积压

安全 redaction、PubSec/EFOpen/加密写回、OCR 文字层、高保真转换、TTS、OPDS/LCP、
完整应用服务与新增罕见格式子特性按真实需求重新立项，不自动列入下一核心版本。
JPX/JBIG2、Pattern、复杂色彩/透明组合或 CSS 余项若被 R2 证明阻碍常用文档，应按影响提升为阅读缺陷任务。
已发布接口的正确性、安全清理和依赖许可继续维护。未来交付面向最终用户的宿主仍需相应无障碍与真机验收，
它们属于宿主出口，不能用核心 SDK 通过替代。

核心版本的完成依据是：声明范围内可靠阅读、预算满足、可安装接入、依赖/许可清晰和可追溯发布。
不再用历史二十项功能的完成比例衡量核心版本。
