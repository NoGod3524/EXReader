# Windows 原生书内搜索候选

从 G1 共同源码证据 HEAD `3bcc6511` 独立接续，分支 `codex/reader-windows-search-ui`。
默认配置不加入搜索；Windows账号宿主显式开启 `EXR_READER_WINDOWS_SEARCH` 后消费安装后的原样F1。

次级“书内查找”入口和 Ctrl+F 打开原生编辑框/32行结果列表；查询、下一批、定位、取消和关闭在面板内可达。逐字区分大小写，不包含OCR。SDK/产品schema/wire/预算不改。

每个现有串行worker内创建F1句柄、恢复纯值cursor、取最多32项、复制selector、释放结果并关闭句柄，不跨OS线程保留F1句柄。UI仅持有自有副本。原书SHA-256、长度、格式、投影版本绑定到打开的阅读会话；扫描和定位重新核对，变化则拒绝并要求重新打开。定位先在独立SDK对象上得到FOUND，再交现有renderer路径重新验证；固定页只按稳定page ID解析，不使用页号/旧偏移回退。恰好满批后的空尾批保留上一批结果。

源码 `e4bddc31` 的首轮 `40128929347` 和诊断增强源码 `2d2bb59e` 的第二轮 `40129875990` 均编译、安装成功，原F1消费者264项通过；初始TXT UI均在导入后等待书架行超时，搜索控件检查执行0项，验证记录仍为 `accepted=false`。第二轮明确失败阶段为 `wait-imported-row`；打印中文原生状态时又遇到控制台cp1252编码异常，现将诊断保存到JSON并以ASCII转义输出。原失败工件均保留。

只读诊断 `40130113080` 认证并读取首轮工件 `12574561832`（35,586,388字节，SHA-256 `bca45709f53eabff6d90a731a90fcb2cc51964f031ed8fd7a44e63c6d5bd4b61`），确认SDK书表为空；该诊断不授予功能。

初始TXT控件检查不替代EPUB/PDF、实时取消、错源、换书/关闭/重启、键盘及UIA完整验收。后续还须同源执行保留的Windows检查与严格工件认证。
