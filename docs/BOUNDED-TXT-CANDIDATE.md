# Bounded TXT candidate: projection and selector stage

This is an incomplete SDK candidate based on b723a9a3a20af7b31729fa1a47b695b20a0c4b8f. The opt-in `exr_txt_scan_source` streams an immutable source into paragraph callbacks using whole-document projected UTF-8 byte offsets. It decodes BOM-marked UTF-16 and UTF-8, normalizes newlines, trims and omits empty paragraphs as the snapshot parser does, handles short reads and cancellation, and rejects an indivisible decoded line above 64 KiB. Callbacks can have already run when an error is returned; callers must discard their own partial state. An exact streaming search reuses this projection and matches across paragraph boundaries, with bounded query scratch. These primitives do not retain the source or establish its identity.

`exr_txt_anchor_create_source` makes a bounded quote selector using the existing `exr_anchor_create` implementation on a small normalized context window, retaining whole-source byte offsets. The entire source is validated on each call. The host must bind that selector to the identity of the immutable original bytes; this operation does not establish or verify identity, resolve selectors, or persist them.

The Windows workflow exercises the installed API against small snapshot projections and selectors, short reads, encoding errors and cancellation, and scans the diagnostic's original deterministic fixture with hash checks. This is a primitive test, not product acceptance or a memory-budget measurement.

The installed candidate now also exposes an owned-source continuous pager; see [the view observation](bounded-txt-view-candidate.md). Remaining work includes transactional source import with distinct storage mode and original-byte identity, product search integration, persisted progress/bookmark/annotation anchors and migration, Windows integration, and full end-to-end budget and compatibility acceptance. Existing snapshot APIs and product paths remain unchanged.

## Windows integration boundary (not product acceptance)

The Windows host in `examples/reader.c` imports TXT using `read_import_file` and `exr_library_import_unique`, and opens it with `exr_library_document`. The public library source/file import contract supports EPUB/CBZ (and PDF through file import), but explicitly rejects TXT. Therefore changing the host to call the existing streaming library import cannot store this TXT; a separate durable product-owned storage mode and its catalog/identity mapping are required. It must retain original bytes, authenticate them on reopen, handle interrupted import and deduplication without orphaning or conflating existing SDK rows, and preserve deletion and synchronization semantics. Existing `exr_library_source` objects also become invalid after a commit from another connection; any design using them must account for that lifetime contract.

The host's `bounded` flag currently means EPUB: it expects a publication, chapter-local text reads and anchor resolution. The TXT pager explicitly does not supply those pager queries. `render_reflow`, search, selection, records, and progress cannot safely be redirected to that flag without separate TXT implementations. The source scanner and anchor capture are useful primitives, but capture alone is not selector resolution. Progress must be bound to the verified original identity and saved and recovered through a durable path, including refusal to overwrite on mismatch or failure. Theme CSS is also unsupported by the candidate pager. None of these gaps has been implemented or accepted here.

The installed consumer `bounded_txt_library_boundary` records the streaming-import rejection and checks ordinary unique TXT import, deduplication, snapshot access, and source bytes. It is a diagnostic, not a Windows host test, a large-file import, or component-budget evidence. The candidate workflow uses `pipefail` for the fixture pipeline so failures from the Python driver cannot be hidden by `tee`.
