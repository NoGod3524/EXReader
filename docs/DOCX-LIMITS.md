# DOCX Explicit Limitations and Conservative Preservation Behavior (`DOCX-LIMITS`)

EXReader's DOCX bridge (`exr_edit_docx_read` / `exr_edit_docx_write`) and table/paragraph editing model (`exr_edit_*`) follow a strict **zero-silent-data-loss** policy. Structures outside the editable model subset are never stripped or flattened; instead, they are either **retained byte-for-byte** as opaque XML spans + untouched OPC package parts or **explicitly rejected with `EXR_UNSUPPORTED`** when an API call attempts to mutate them in place.

## Summary of Explicitly Unsupported Structures

| # | Structure / OOXML Elements | Why Active Editing / Layout Is Unsupported | Conservative Runtime Behavior |
| --- | --- | --- | --- |
| 1 | **Word Drawing Canvas** (`wpc:wpc`, `mc:AlternateContent` canvas branches) | Drawing canvases require a nested 2D coordinate composition engine and group connector routing not modeled by the reflow/editor layout tree. | **Byte-for-byte retention**: Decoded inside `<w:r><w:drawing>` as `EXR_EDIT_OPAQUE_RUN`. Round-trip and neighboring paragraph/run edits preserve the exact XML slice and all linked OPC relationships/media parts. Direct run property edits (`exr_edit_set_run_props`) or mid-run splits (`exr_edit_split_paragraph` with non-zero offset) on an opaque run return `EXR_UNSUPPORTED` / `EXR_ARGUMENT`. |
| 2 | **SmartArt Diagrams** (`dgm:relIds`, `word/diagrams/data*.xml`, `layout*.xml`, `quickStyle*.xml`, `colors*.xml`, `drawing*.xml`) | SmartArt diagrams depend on proprietary layout algorithms (`dgm:layoutDef`) to regenerate shapes when nodes change. | **Byte-for-byte retention**: The host `<w:r><w:drawing>` is preserved as `EXR_EDIT_OPAQUE_RUN`, and all `/word/diagrams/*` OPC parts and `.rels` entries are copied untouched on `exr_edit_docx_write`. Zero diagram data is dropped. |
| 3 | **OLE Embedded Objects & Package Embeddings** (`w:object`, `o:OLEObject`, `v:shape`, `word/embeddings/*.bin`, `*.xlsx`) | OLE objects encapsulate external binary compound documents (e.g., Excel sheets, Visio drawings, Equation 3.0 binaries) that require host COM servers to edit. | **Byte-for-byte retention**: `<w:r><w:object>...</w:object></w:r>` is classified as `EXR_EDIT_OPAQUE_RUN` (and top-level non-paragraph containers as `EXR_EDIT_OPAQUE_BLOCK`). All binary parts under `word/embeddings/` and preview images under `word/media/` are preserved byte-for-byte. |
| 4 | **ActiveX Controls & Legacy Form Controls** (`w:control`, `w:AltChunk`, `word/activeX/activeX*.xml`, `activeX*.bin`) | ActiveX controls execute platform-specific COM binaries (`CLSID`) and carry opaque binary persistence streams (`activeX*.bin`). | **Byte-for-byte retention + mutation refusal**: Retained verbatim as `EXR_EDIT_OPAQUE_RUN` / `EXR_EDIT_OPAQUE_BLOCK` along with all `word/activeX/*` parts. Attempting to delete or overwrite an `EXR_EDIT_OPAQUE_BLOCK` via `exr_edit_delete_block` or `exr_edit_set_paragraph_props` returns `EXR_UNSUPPORTED`. |
| 5 | **Structured Document Tags (Content Controls) & Custom XML Data Binding** (`w:sdt`, `w:sdtPr`, `w:dataBinding`, `customXml/item*.xml`) | Live XPath two-way data binding between `customXml` parts and `<w:sdtContent>` requires an XML schema/XPath evaluation engine during editing. | **Byte-for-byte retention + mutation refusal**: Body-level `<w:sdt>` blocks are stored as `EXR_EDIT_OPAQUE_BLOCK` and inline `<w:sdt>` elements as `EXR_EDIT_OPAQUE_RUN`; `customXml/*` parts are preserved byte-for-byte. Attempting to edit or delete an opaque `<w:sdt>` block through paragraph APIs returns `EXR_UNSUPPORTED`. |
| 6 | **Tracked Changes (Revision Marks) & Property Change History** (`w:ins`, `w:del`, `w:moveFrom`, `w:moveTo`, `w:pPrChange`, `w:rPrChange`, `w:sectPrChange`, `w:tblPrChange`) | Accepting, rejecting, or coalescing multi-author revision trees requires revision-aware conflict resolution across paragraph and section boundaries. | **Byte-for-byte retention**: Inline `<w:ins>` / `<w:del>` nodes inside paragraphs are kept as `EXR_EDIT_OPAQUE_RUN`, and `*PrChange` child elements inside `<w:pPr>`, `<w:rPr>`, `<w:sectPr>`, and `<w:tblPr>` are preserved in ECMA-376 schema order when sibling properties are edited. |
| 7 | **Complex Table Cells: Merged (`gridSpan`/`hMerge`/`vMerge`), Shaded (`w:shd`), Nested Tables (`w:tbl`), and Multi-Paragraph/List Cells** | `exr_edit_table_set_cell_text` is a single-paragraph plain-text replacement command; applying it to a merged, shaded, nested-table, or multi-paragraph cell would destroy cell spans, shading, subtables, or paragraphs 2..N. | **Explicit `EXR_UNSUPPORTED` guard + byte-for-byte retention**: `exr_edit_table_decode` sets `cell->unsupported` (`EXR_EDIT_CELL_MERGED`, `EXR_EDIT_CELL_SHADING`, `EXR_EDIT_CELL_NESTED`, `EXR_EDIT_CELL_OPAQUE`). Calling `exr_edit_table_set_cell_text` on any guarded cell returns `EXR_UNSUPPORTED` without modifying the cell. Calling `exr_edit_table_insert_row` or `exr_edit_table_delete_row` across an active `w:vMerge` continuation chain also returns `EXR_UNSUPPORTED`. |
| 8 | **In-Place Editing of Complex Field Codes (`w:fldSimple`, `w:fldChar`/`w:instrText`), Comment Ranges, Bookmarks, and DrawingML Textboxes (`w:txbxContent`)** | Fields (`PAGE`, `NUMPAGES`, `DATE`, `REF`, `TOC`), comment range markers (`w:commentRangeStart`/`End`), bookmarks (`w:bookmarkStart`/`End`), and shapes with `<w:txbxContent>` span multiple XML tokens or sub-trees outside plain `<w:r><w:t>` runs. | **Byte-for-byte retention as `EXR_EDIT_OPAQUE_RUN`**: Each non-plain child of `<w:p>` is isolated as an `EXR_EDIT_OPAQUE_RUN`. Neighboring plain-text `<w:r><w:t>` runs in the same paragraph can be freely edited or split while the field codes, bookmark anchors, comment anchors, and `<w:txbxContent>` sub-trees remain byte-identical. |

## Verification Guarantees

1. **No Silent Drop**: Unrecognized or unsupported elements in `word/document.xml` are captured by exact byte-span slicing (`source_xml` Expat byte offsets) and emitted verbatim on `exr_edit_docx_write`.
2. **Non-Main Part Preservation**: All OPC package parts other than the edited `word/document.xml` (and `word/_rels/document.xml.rels` / `[Content_Types].xml` when new PNG images are explicitly inserted) are written back byte-for-byte identical to the input archive.
3. **Transactional Atomicity**: Any command returning `EXR_UNSUPPORTED` or `EXR_ARGUMENT` marks the active `exr_edit_tx` transaction as failed so `exr_edit_commit` automatically rolls back all prior changes in the batch.
