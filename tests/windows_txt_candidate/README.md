# Experimental bounded TXT consumer

This separate consumer uses the unchanged installed SDK. It reads at most 64 KiB and 512 LF-terminated lines per window from an immutable `exr_source`; the SDK decodes each window and constructs an ordinary complete document for it. The returned source-byte cursor is committed only after success. The minimal host renders a first page, searches one window, and captures and resolves an anchor after reloading that same window. It does not modify the input file.

The candidate intentionally rejects UTF-16, CR line endings, a line that does not fit its window, and a UTF-8 BOM starting a noninitial window. Other malformed UTF-8 is rejected by the SDK. It is not a replacement for `exr_document_open_memory`: use only cursors previously returned for the same immutable source. Its decoded positions are window-local, not old whole-document offsets. Cancellation is checked around source reads and after the SDK parse; the frozen parse call itself is not interruptible by this adapter.

Unresolved: a window starts a fresh pager, so layout can change at the boundary. Queries and text selectors do not cross windows. The sample anchor only round-trips in one unchanged window; source identity validation, durable source-to-projection offsets, old bookmarks and annotations, cross-window selections, global search, arbitrary recovery, and page-equivalent continuation remain unimplemented. The Windows product catalog cannot import this input with the frozen TXT import, and its bounded host route is EPUB-only. This test host does not integrate with that catalog or claim to fix product import. Supporting existing decoding semantics and a continuous bounded pager requires further implementation and tests before any product use.

The Actions workflow checks a 513-line projection against the frozen full-document API and reports its boundary-page ranges. It also regenerates the original performance sample, verifies its known size and SHA-256 before and after use, and runs the separate host three times. The peak working set belongs to the whole test process; `max_document_bytes` is an SDK-owned document payload measurement, not a complete parser workspace measurement. Neither proves the old product performance budget or product regression suite.
