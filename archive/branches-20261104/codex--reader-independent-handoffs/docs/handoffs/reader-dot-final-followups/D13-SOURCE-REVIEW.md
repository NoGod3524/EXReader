## 已存在的保护

- WebDAV临时文件拒绝不合法叶名、保留设备名和已存在目标，刷新后不覆盖发布。
  POSIX在webdav.cpp:186打开目录fd，195以openat/O_EXCL/O_NOFOLLOW创建，243用同一目录fd发布；
  清理也用unlinkat。Windows在175检查目录属性、181以CREATE_NEW/OPEN_REPARSE_POINT建文件，
  230使用不替换的MoveFileEx。这里描述调用方式，未动态验证中途路径变化。
- cloud_import.c:535在下载发布后独立按64KiB读取计算长度/SHA；653在导入前再次重读，
  与staged保存的长度/SHA不符就返回CORRUPT，不进入SDK。
- sideload.c:131重新打开路径。非PDF保留该次打开的FILE作为随机读取source（153），
  EPUB/CBZ走source入口，其他重排格式有有界内存复制；保持既有格式上限和取消检查。
- 成功SDK提交与stage清理回执分列，后续取消或清理失败不删除已提交书籍。

## 静态可见的连续身份缺口

1. staged结构在cloud_import.c:18只保存路径、名称、长度、格式和SHA，不持有文件/目录句柄或OS文件身份。
   rc_hash_file在287以路径打开并在返回前关闭。下载后校验、导入前校验和后续读取是不同的打开操作。
2. 导入前SHA核验结束后，676仍把路径交给exr_sideload_import_file；在此链上未见把同一个已核验句柄
   传递到SDK。SHA相等可说明该次读取的内容相同，不能单独证明随后重新打开时仍是同一对象。
3. PDF在sideload.c:159再把路径交给SDK文件入口；公开合同已明确稳定路径前置条件，
   当前wrapper先前持有的FILE不等于SDK所有后续打开均使用该句柄。
4. cloud_import.c:94使用fopen/_wfopen；在这层未见逐组件nofollow/OS file-id复核。
   Windows WebDAV的目录属性检查与之后按路径建文件/发布不是同一个目录句柄操作。
   POSIX的目录fd有较强的本次发布锚定，但发布后cloud模块仍重新解析完整路径。
5. cloud_import.c:108/701按保存的路径删除stage，未见清理前核验该目录entry仍属于原staged对象。
   这只是清理身份校验的源码缺口，不是canary被删除或配置根已被逃逸的运行证据。

上述缺口不构成已复现漏洞。若宿主确实保证私有目录和文件在整个交接区间不可由其他写入者改变，
需要分别证明该前置条件；仅把目录命名为private或持有一个opaque staged值不足以充当OS证据。
同时，本次也没有证明任何进程能够实际改变该目录、赢得时序或导入其他原件。
