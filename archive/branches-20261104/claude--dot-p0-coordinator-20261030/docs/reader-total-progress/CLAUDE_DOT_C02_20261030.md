## What exists
* `extras/migration/windows_coordinator_20261030/` — standalone C library
  `exreader-migration-coordinator` (no SDK, `lm_main`, CMake-routing or host dependency).
  * Public header `exr_wc.h`: binding, logical snapshot records, gates, journal, `wc_run`, `wc_recover`.
  * Private provider header `exr_wc_provider.h` (installed under `private/`): provider function table and the
    reference filesystem provider.
* "full49": every identity is the full-width 49-byte form (volume64 + FileID128 = 48 lowercase hex + NUL), matching
  the existing qualified Windows adapter IDs. Snapshot records, lease and staged identities are all 49 bytes; the
  coordinator never truncates or reinterprets them.
* Binding: source commit (40 hex), Actions run id, run attempt, artifact SHA256, platform, SDK identity and provider
  identity SHA256 are hashed into one binding digest that is carried by every journal line and by the snapshot digest.
  A provider whose `identity_sha` differs from the binding is refused.
* Logical snapshot: path-sorted, unique, canonical relative paths, each with full source identity, size and SHA256.
  `snapshot_digest` includes ids and binding; `content_digest` is path+size+hash only (used for import verification).
* Orchestration (`wc_run`): preflight → admit (lease) → snapshot → import (staged) → verify → publish → release →
  complete. A hash-chained, sealed, write-ahead journal line is appended through the caller's sink **before** every
  mutating provider call; a failed append stops the run (before publish intent: nothing is published).
* Recovery (`wc_recover`): validates the whole chain and binding, then decides from the last durable state. It asks the
  publisher/engine for the actual publication state, never guesses: undecidable → `WC_UNCERTAIN`, everything retained.
* Missing provider function or gate evidence → `WC_PENDING` with the named missing items; **zero provider calls and zero
  journal lines**. `WC_COMPLETED` needs all five gates (admission, publisher, recovery, observer, fault) *and* every
  provider function.
* Reference filesystem provider (real): recursive snapshot (reparse/special files refused, depth ≤ 8), exclusive
  staging directory `.exwc-<run>-<attempt>` (never adopts an existing one), copy with hash-while-copy (source change
  during run fails the import), re-walk verification, and conservative discard that removes only paths it created and
  retains foreign content (`WC_STEP_UNCERTAIN`).

## Not duplicated / not provided (explicit pending)

* Native publisher exclusive publication/rename custody → provider `publish`/`recover` (gate `publisher`).
* Native recovery engine and observer → gates `recovery`, `observer`.
* P0 fault acceptance → gate `fault`.
* No `lm_main`, CMake routing, host seam or production-owner edits. No SDK edits.

## Interface proposals for the manager
1. C01: expose `admit(binding) -> lease49` and idempotent `release(lease49)`; `release` may be called again by recovery
   after a crash between "release begin" and "release ok".
2. Publisher: `publish(staged49) -> {YES,NO,UNKNOWN}` and `recover(staged49)` returning the *actual* on-disk state;
   YES/NO must be authoritative, UNKNOWN keeps the run `WC_UNCERTAIN`.
3. Gate evidence: each owner supplies a 64-hex digest of its Actions artifact; the host passes them in `wc_gates`.
4. The host (a later, separately approved seam) supplies a durable journal sink (append + flush + return 0).

## Known deficiencies
* Never run against the real Windows publisher, recovery engine, observer or host lifecycle.
* No power-loss / directory-fsync claim. The journal is only as durable as the caller's sink.
* The filesystem provider buffers each file in memory (≤256 MiB per file) and does not copy ACLs/timestamps.
* Single staging directory per run id/attempt; no cross-volume handling.
