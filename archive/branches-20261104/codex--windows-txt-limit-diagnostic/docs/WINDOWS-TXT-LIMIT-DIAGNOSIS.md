# Windows 多行 TXT 限额诊断

## 原始完整宿主证据

完整产品运行 [40399315487](https://github.com/NoGod3524/EXReader/actions/runs/40399315487)，源码 `7aab6e559d17e730067594ee7da5189bf00f6dd8`，第 1 次尝试。输入为 16,792,975 字节，SHA-256 `4f45393b25817f506a51b56cc5d61599556e4dd5b0bd59aa00f7eb43cbfc0a86`。三次真实导入都返回 `EXR_LIMIT`；记录显示没有导入书目或路径映射，搜索结果为零。该失败仍然存在，不视为性能验收通过。

生成器每组有 513 个非空行、40,465 字节；按生成器的完整组数计算，样本包含 415 组，即 212,895 个非空行。这里的行数是依据生成器计算，不是对原文件的独立实测。

原始工件 ID `12688856368`，ZIP SHA-256 `7d4b5189a6fabdda7f03a1a8fadb8aed0bff806dc11a4555a3f7d20f5838b008`。完整产品可执行文件 SHA-256 `2c460d6775e9a0c798c80abcf72e468b2d15c85be9967f8058095794a2c0ad4c`；产品包 ZIP SHA-256 `75f0546191825a0942ad4a8f5100f8fe1d50301a65ec8835f08247b220aae979`。独立认证及读取原始工件见 [40401415853](https://github.com/NoGod3524/EXReader/actions/runs/40401415853) 和 [40402103092](https://github.com/NoGod3524/EXReader/actions/runs/40402103092)。

三次失败的宿主进程峰值工作集分别为 136,548,352、136,343,552、136,065,024 字节；对应关闭时 private bytes 为 28,803,072、29,786,112、28,831,744 字节。后者是关闭时读数，不是私有内存峰值。进程峰值是整次宿主生命周期的工作集峰值，不是单独解析器的分配量。

## 边界与原因

[40401376637](https://github.com/NoGod3524/EXReader/actions/runs/40401376637) 用公开 `exr_document_open_memory` 进行 Windows SDK 对照。每行 64 个字符加换行：131,070 行和 131,071 行成功；131,072 行返回 `EXR_LIMIT`。另一输入为 10,000 行、17,010,000 字节，成功。该对照中的 SDK 源码与原始产品及本分支的 `src`、`include`、`cmake` 和顶层 `CMakeLists.txt` 相同；它不是原始完整宿主程序的重跑。

现有纯文本解析将每个非空行作为一个块；构建公开文档树时，产生两个根节点，以及每个块各一个段落节点和一个文本节点。`EXR_MAX_NODES` 为 262,144，因此 131,071 行恰好对应 262,144 个节点，下一行超出上限。原始样本按生成器计算需要 425,792 个节点。输入字节数、文本预算和块数上限均不能单独解释这组边界。

公开错误将节点上限和若干分配失败合并为 `EXR_LIMIT`；原始失败没有记录具体分支。因此，代码中的节点计数与公开 SDK 对照共同强烈支持节点上限是原因，但原始运行的错误记录本身不能排除分配失败。

## 修复范围

`exr_document_nodes` 公开借用的连续完整节点数组，节点关系、文本及偏移均可观察。合并行或移除文本节点会改变公开树，也需要证明段落、分页、查找和锚点行为仍符合约定；简单改用 EPUB 的内部按章视图并不能提供同一 TXT 公共快照。保持每行两节点并维持现有节点预算时，该样本无法装入现有完整树。

尚未找到在冻结预算下同时维持这些语义的已验证实现，故没有修改生产代码或把失败改为通过。后续可评估有界 TXT 读取与稳定源位置的新接口及宿主集成，并以段落、分页、查找和锚点回归验证兼容性；此项需要明确 API 方案和实际资源验证。

## 独立候选与实际缺口

`tests/windows_txt_candidate` 为单独的实验消费者，不修改 SDK 或产品宿主。它从不可变源按 LF 行边界读取至多 64 KiB、512 行的窗口，再交给原有 TXT 解析器和分页器。它保留源文件字节，返回源字节游标；支持的范围和错误情况见该目录的 README。

[Windows Actions 40404060097](https://github.com/NoGod3524/EXReader/actions/runs/40404060097) 对源码 `4ae04f32a9a0e4d158b3f14498cdea9da833d6ba` 校验冻结 SDK 路径未变，安装后的五项消费者测试全部通过。重建的原始样本验证 SHA-256，读取前后文件一致；三次独立测试宿主均扫描 212,895 个段落、416 个窗口，每窗口最多 1,026 个节点、184,652 字节的 SDK 文档对象。整个进程峰值工作集分别 6,283,264、5,894,144、6,004,736 字节，测试计时 298.659、307.086、298.175 毫秒，包含全文件分窗解析、首屏和单窗口锚点重载，不包括产品导入和整书分页。测试宿主可执行文件 SHA-256 为 `67a50647552375c1c54ffc1c973e05900d136d19e2ca56927d51e4ae5fa7d7e7`。SDK 文档对象大小不包括全部解析工作区；这些数字不能用作产品预算验收。

小样本中分窗投影与完整文档逐字一致，但分页边界不一致：第 28 页的分窗结束偏移为 2559，完整文档为 2564。这是实测兼容缺口，不能将独立窗口当成连续分页实现。现阶段只验证单窗口搜索与锚点重载，尚无跨窗口查找、连续分页、完整 UTF-16/CR 解码、持久源身份及旧书签和标注兼容。冻结 SDK 的 TXT 书架导入仍先构建完整文档，Windows 有界宿主入口目前是 EPUB；本候选尚未接入产品目录，真实目标仍未完成。
